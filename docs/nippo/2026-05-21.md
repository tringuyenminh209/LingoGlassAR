扱われるため、phone 側で 24 kHz 録音すれば server-side resampling
不要となり レイテンシ + コストともに削減。

| 項目 | 結果 |
|---|---|
| ブランチ | feat/s1-day-5-audio-recorder OK |
| scope | mobile/lib/audio/recorder.dart + test + pubspec のみ |
| sample rate | PCM16 mono 24 kHz、100 ms = 4800 bytes チャンク |
| DI 設計 | `@visibleForTesting` `AudioRecorderDriver` interface 提供 |

#### Incident 1 (build): flutter_sound caret bump → AGP 8 namespace 違反

`pubspec.yaml` の `flutter_sound: ^9.2.13` は CI で 9.30.0 に解決され、
9.30.0 は `StreamSink<Food>` API を捨て `StreamSink<Uint8List>` に

を `build.gradle` に宣言せず AGP 8+ で build 失敗。

修正 (`5cfb5be`): flutter_sound を `^9.30.0` に上げ、`recorder.dart`
を Uint8List 流に書き直し (`Food`/`FoodData` envelope 廃止)。
副作用で `uuid` 衝突が出たので `^4.5.0` のまま維持。

#### Incident 2 (build): NDK + minSdk 不足

build エラー2 連発: `5 plugins require NDK 27` (flutter は 26) +
`flutter_sound minSdk 24 > project 21`。

修正 (`dc1ff73`): `android/app/build.gradle.kts` で
`ndkVersion = "27.0.12077973"` + `minSdk = 24`。
Android 7.0 (2016) 以上を要求するが 2026 年時点で >99% カバー、
S0 BLE-only 制約の `minSdk 21` から bump しても問題なし。

#### Incident 3 (runtime): PTT 状態 race + permission concurrent request

実機テスト 1 回目で `endUtterance error: Bad state`, `already
connected or connecting`, `PermissionManager: already running` が
連発。原因 3 つ:
1. press down 中に WS が `connecting` 中のまま release で
   `endUtterance` を叩く
2. press down 中に release が割り込み、teardown 後に元の chain
   が完走して二度目の connect/start
3. `permission_handler` が同時に 2 回 request されてエラー

修正 (`17ecb3f`):
- `_PttState` enum (`idle/starting/recording/ending/aborting`) を
  TranslateScreen に追加
- `_onPressDown` の各 await の直後に `if (_ptt != _PttState.starting)
  return` チェックポイント、release 中なら orphan socket をクリーン
  アップして idle に戻す
- `_bootstrap` でアプリ起動時に `Permission.microphone.request()` を
  1 回だけ実行 (pre-warm)、recorder.start 内では grant 確認のみ

#### Incident 4 (server): 24 kHz fallback drift + opaque TranslatorError

実機テスト 2 回目で `TranslatorWsError(invalid_event): invalid event`
と `TranslatorWsError(translator_error): OpenAI Realtime WebSocket
failed` が交互に出た。

調査:
- Docker image が `docs/` をコピーしないので backend は
  `sessions.py` 内の `_WS_SCHEMA_FALLBACK` を使う。これが
  `sampleRateHz: const 16000` のまま (Day 3 で 24 kHz に変更した
  canonical schema と drift) → mobile の 24000 チャンクが reject
- translator.py の `TranslatorError("OpenAI Realtime WebSocket
  failed")` が wrap で原因を捨てていた → 真因不可視

修正 (`4c58762`):
- 埋め込み schema fallback を `sampleRateHz: const 24000` に同期
- `TranslatorError(f"...: {type(exc).__name__}: {exc}")` で原因クラス
  と message を露出

→ ここで初めて真因が wire に出た:

```
ConnectionClosedError 4000 invalid_request_error.beta_api_shape_disabled
```

#### Incident 5 (API contract): OpenAI が beta Realtime shape を停止

OpenAI が beta Realtime API shape (`OpenAI-Beta: realtime=v1` header,
flat `input_audio_format`, `modalities`, `gpt-4o-realtime-preview`
model) を 2026 で disable。GA shape に移行する以外に手段なし。

修正 (`dfa12e1`):
- model: `gpt-4o-realtime-preview` → `gpt-realtime` (GA)
- header: `OpenAI-Beta: realtime=v1` を削除
- `session.update.session`:
  - `type: "realtime"` (新規必須)
  - `modalities: ["text"]` → `output_modalities: ["text"]`
  - `input_audio_format: "pcm16"` (string) →
    `audio.input.format: {type:"audio/pcm", rate:24000}` (object)
  - `input_audio_transcription` → `audio.input.transcription` に
    階層化
- `response.create.response.modalities` → `output_modalities`
- receive 側は `response.output_text.{delta,done}` (GA) と
  `response.text.{delta,done}` (legacy alias) の両方受理
- `conversation.item.input_audio_transcription.completed` は GA
  でも同名、source_text 取り込み変更なし

backend unit test (3/3) は legacy alias を受理する受信パスにより
そのまま pass。push 済み (`dfa12e1`)、anh が EC2 で

### Day 7 の学び

1. **OpenAI Realtime はもう beta shape を受け付けない**。preview model
   名 + `OpenAI-Beta` header + flat session config の組合せは 2026 中
   に完全に消える。GA 仕様 (gpt-realtime, session.type=realtime,
   audio.input.format object, output_modalities) に揃えること。
2. **embedded schema fallback は drift する**。Docker image に
   `docs/` を含めない設計を取った代償。Day 3 で予見されたが Day 7 で
   ヒット。Day 8 着手前に vendor 方針を決める。
3. **state race は press/release のような discrete event でも発生
   する**。タップは早い人で 50 ms 切る。async chain が完走する前に
   次の event が来る前提で書く必要あり。enum-based state machine +
   each-await checkpoint がシンプルかつ確実。
4. **エラーの wrap で原因を消すと debugging 時間が直接損失**。
   TranslatorError は最初から `from exc` で原因を保持していたが、
   message string には反映されていなかった。wire に出る文字列にも
   `type(exc).__name__: exc` を含めると一段で真因に到達。
5. **Codex 委譲 vs 自作の判断基準**。3 つ以上の async サービスを
   束ねる glue code は state machine の設計判断が中心になり、
   prompt 化より直接書く方が速い。Codex は単一ファイル + 明確な
   入出力契約 のタスクで強い。
