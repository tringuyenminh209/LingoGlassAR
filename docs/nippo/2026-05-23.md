- **sub-stage target は zero-sum trap**: STT を速くしようとしたが、
  translate 側が遅くなって相殺。end-to-end 視点なら 3 つの config は
  ほぼ等価。最初から system_latency_ms を probe target にしていれば
  Day 1 で「optimisation 余地なし」と判定できた。今回の retro が
  feedback memory として永続化される。
- **streaming model ≠ faster model**: 「streaming-first」は partial
  の到着パターン (incremental tokens) を指すのであって、first
  partial までの total time-to-text を指さない。OpenAI 広告の
  200-400 ms はインスタンス warm 状態のサーバ側 inference のみで、
  クライアントから見た end-to-end ではない。phone→Osaka EC2→US
  OpenAI のネットワーク leg だけで RTT 300-500 ms あり得る。
- **same-day Day 1 → Day 3 圧縮のリスク**: 「次回 X 月 Y 日」と書く
  たびに同日中に Y 日分を押し切る癖が S1 Day 8-10、S2 Day 1-3 で
  3 連続で発生。smoke が payload shape を救ったが hypothesis 自体は
  救わなかった。「寝かせて翌朝もう一度 probe assumptions を見る」
  ステップを skip した影響。次の sprint では Day 境界を 1 暦日に
  揃えるか、同日圧縮するなら mid-day で hypothesis review を挟む。
- **revert は失敗ではない**: 2 回の device bench で root cause を
  特定 → free trim だけ残して革命的な変更は撤回 → criterion 自体を
  amend、という流れは「実験 → 反証 → criterion 修正」の正攻法。
  日報に学びとして残しておけば、将来「あの S2 Day 3 で何があったか」
  が後追いで分かる。
