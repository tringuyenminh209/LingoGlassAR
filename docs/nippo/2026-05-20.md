## 本日の作業内容

### 1. Phase E レビュー残課題対応
- P2 ブロッカー修正: `SubtitleAssembler::feed()` で stale (古い `sequence_id`) チェックを fragment_count / fragment_index のバリデーションよりも前に移動。malformed な stale packet が active buffer を破壊する不具合を解消。
- リグレッションテスト 2 件追加 (合計 16 ケース)。
- 携帯側 (`BleTransport`) で `device.connectionState` を購読していなかった不具合を修正。OS側で BLE 切断 (Bluetooth トグル等) しても "already connected" 状態にロックされ、`writeCharacteristic` が `device is not connected` で失敗していた。

### 2. Phase F 実装
- **firmware**: ACK ペイロードを 2 バイトから 10 バイトに拡張。`t_recv_ms` / `t_render_ms` (uint32 LE) を追加。`g_seq_in_progress` / `g_seq_recv_ms` で sequence ごとの開始時刻を ESP32 `millis()` で取得。
- **mobile**: `LatencyLogger` サービス新規作成。`send_ts` を記録し、ACK の sequence_id でマッチング → `LatencyRecord` (RTT ms + fw_proc ms) を蓄積。`Run 20` ボタンでウォームアップ 4 + JP MTU サイクル 8 + ショート連発 8 を実行し、p50/p90/p95 を画面ログに出力。Copy CSV ボタンでクリップボードにエクスポート。
- **tooling**: `tools/latency_report.py` (標準ライブラリのみ) で CSV を MTU グループ別に集計し markdown 形式でレンダリング。

### 3. 実機 Run 1 完了
- Samsung Galaxy S10 + ESPr Developer S3 + 0.96 inch I2C OLED で 20 サンプル取得 (`out/run_2026-05-20.csv`).
- 結果:
  - MTU 247: p95 = **199.9 ms** (バジェット 200 ms に 1 ms 差で収まる)
  - MTU 185: p95 = 240.2 ms (40 ms オーバー)

- 判定: **CONDITIONAL GO** (operating MTU 247 では budget 内、ただし MTU < 185 は製品側でブロックする条件付き)

## 課題・懸念

- **p95 199.9 ms はバジェット上限ギリギリ**。RF環境やOS jitter で簡単に超える可能性あり。Run 2 を別の日 (Wi-Fi 2.4 GHz が空いている時間帯) に実施して安定性確認が必要。
- **OLED 描画コストが 32 ms 固定**で底になっている (U8g2 sendBuffer over I2C 400 kHz)。将来 dirty-rect 戦略か I2C 1 MHz 化を検討する余地あり。
- **MTU 23 は使用不可レベル**。製品側で MTU < 185 のとき "degraded mode" バナーを出し subtitle 送信を抑止するロジックが S1 に必要。
