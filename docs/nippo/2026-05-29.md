### 不具合 1: 撮影一発目でアプリがクラッシュ

- `ClassNotFoundException: com.google.mlkit.vision.text.japanese.JapaneseTextRecognizerOptions$Builder`。
- 原因: `google_mlkit_text_recognition` プラグインは Latin モデルのみ同梱し、JP/CN/KR/Devanagari は `compileOnly`（app size 削減のため）。Latin は動くのでアプリ起動は通るが、`TextRecognitionScript.japanese` を呼んだ瞬間にクラスが無く落ちる。
- 修正: `mobile/android/app/build.gradle.kts` に `implementation("com.google.mlkit:text-recognition-japanese:16.0.1")` を追加（プラグイン同梱の text-recognition:16.0.1 にバージョンを合わせる）。**bundled モデル**なので Day 1 で懸念した初回モデルダウンロードのリスクも同時に解消、認識は完全オンデバイスのまま。

### 不具合 2: 「Translation failed」

- `/healthz` は 200 なのに `POST /v1/translate` が 404。
- 切り分け: エンドポイントは `main` に存在（`main.py` が `translate_router` を mount、`7ad32f0`/`731d425`）。つまり EC2 が Day 2 以前のビルドで稼働していた = **デプロイずれ**。コード修正は不要。
- オペレーターが再デプロイ（`git pull` + `docker compose up -d --build`）。`curl POST /v1/translate` で 200 + translatedText を確認、ライブ化。

### 不具合 3: 小さい文字に対して撮影が甘い

- カメラが `ResolutionPreset.high`（~720p）かつ能動的なフォーカス無しで、メニュー/看板の小さな字が滲む。
- 修正（`ocr_screen.dart`）: `veryHigh`（~1080p）へ引き上げ、init 後に `setFocusMode(auto)` + `setExposureMode(auto)`、プレビューにタップフォーカス（`setFocusPoint`+`setExposurePoint`）を追加。max は撮影が遅く OCR 時間を膨らませるだけなので不採用。
- オペレーターが再撮影し、より鮮明になったことを確認。

## 追記（同日）— Day 6 prep（`--s3` レポートモード）

Day 5 クローズ後、続けて Day 6 の Claude prep を実施。

### `tools/latency_report.py` に `--s3` を追加（`render_s3_markdown`）

- 入力は `OcrLatencyRecord` CSV（モバイルの「Copy OCR latency CSV」）。`*_ms` は撮影アンカーからの累積デルタなので `ocr_system_latency_ms == ble_ack_ms` がそのままゲート値。
- **基準 #1（認識）**: key-line pass/fail を domain 別に `% pass` 集計。pass/fail は実行後にオペレーターが目視で付ける追加列 `recognised_pass` から読む（テキストは保存しない、--s2 の accuracy と同じ規律）。`capture_id` を `ocr-NNN` -> `sign-01`.. に貼り替えると domain グループ化される。
- **基準 #2（レイテンシ）**: 完走キャプチャの `p95(ocr_system_latency_ms)` + recognise/translate/ble のレグ分解（累積デルタの差分）。`ble_unavailable`/`no_text` は完走でないので試行にはカウントするがレイテンシ集計から除外。
- ゲート: 認識 >= 80% かつ p95 <= 1500 ms（provisional、device-confirm）。認識は `recognised_pass` 記入まで PENDING、レイテンシ/レグは常に算出（タイミングは即読める）。

### prep/impl split + 検証

- 純 stdlib の決定的なレポート関数（実機パスではない、stub も不要）なので、タスク表どおり Claude が本体 + テストを書いて自己検証。
- テスト 7 件追加（pending / GO / 認識 FAIL / レイテンシ FAIL / レグ分解 / abort 除外 / domain グループ化）。`python -m pytest tools/test_latency_report.py` = **19 pass**（既存 12 + S3 7）、ruff clean、ライブ `--s3` レンダリングも確認。
- 注意: cp932 stdout だと出力の em-dash で落ちるため `PYTHONIOENCODING=utf-8` で実行（root CLAUDE.md 既知事項）。

## 追記（同日）— Day 6 実機プリベンチ + translate トランスポート修正

`--s3` レポートが揃った後、オペレーターが実機で最初の数キャプチャを回した（BLE は 3 本目で接続）。レイテンシ CSV から**重大な発見**。

### 発見: translate leg が毎回 ~4 秒

3 行の leg 分解:

| capture | recognise | translate leg | ble leg | total |
|---|---|---|---|---|
| ocr-001 | 2928（cold） | 4191 | — | abort（ble 未接続） |
| ocr-002 | 889 | 3654 | — | abort（ble 未接続） |
| ocr-003 | 894 | 4589 | 116 | 5599 |

- recognise は 2928 -> 889 -> 894 ms に収束（初回 ~2.9 s は JP モデルロード）。BLE leg 116 ms。**どちらもゲート内**。
- だが **translate leg が全 3 行で ~3.7–4.6 s**。cold-start ではなく系統的。total 5599 ms vs ゲート 1500 ms → **3.7 倍オーバー**。
- **最初の 2 行が `ble_unavailable`** だったのは、OCR 画面が独自の `BleTransport` インスタンスを持ち（音声画面と接続を共有しない）、app-bar の Bluetooth アイコンで接続するまで `_isBleConnected=false` のため。3 本目で接続して初めて完走。

### 根本原因 + 修正

`POST /v1/translate` が**リクエストごとに OpenAI Realtime WebSocket を新規に開いていた**（`Translator.connect()` の WSS ハンドシェイク、EC2 大阪 → OpenAI で ~4 s）。音声パスは PTT 押下時に 1 度開いた session を発話全体で使い回すのでこのコストを償却するが、OCR にはウォームな session が無く、毎キャプチャがハンドシェイク全額を払っていた。Day 1 probe で挙げたリスクそのもの。

**修正方針（ユーザー選択: Chat Completions one-shot）**:
- 新規 `app/services/text_translator.py` の `ChatTranslator` で chat completions（1 回のステートレス HTTP）に切替。モデルは `Settings.translate_model`（デフォルト `gpt-4o-mini`）。
- プロンプトは `SYSTEM_INSTRUCTIONS` を import して単一ソース維持。`TextResult`/`TranslatorError`/`CostUsage` を再利用し、ハンドラの 502 マッピング + コストログは不変。
- 使われなくなった Realtime `Translator.translate_text()` と専用テスト 5 件を削除（no-dead-code 規約）。
- コスト単価は `gpt-realtime` テキスト単価のまま据え置き → 安価な chat モデルを過大見積もり。日次キャップに対しては保守的なので意図的にそのまま。
- プライバシー: ラップする例外メッセージは型名のみ（ソーステキストを 502 ボディに漏らさない）。
