### 1. redeploy 後の translate 実測

オペレーターが backend を redeploy（chat completions 版ライブ）。`POST /v1/translate` を繰り返し叩いてサーバ自己計測の `durationMs`（= OpenAI chat call の所要）を取得（プライバシー: 計測値のみ、翻訳テキストは保存しない）。

| 計測 | durationMs |
|---|---|
| 1回目（cold） | 1873 |
| 2 | 570 |
| 3 | 806 |
| 4 | **3554**（tail spike） |
| 5 | 701 |
| 6 | 495 |

- **median ~500-800 ms**（Realtime ハンドシェイク版の ~4 s から大幅改善）。`total ≈ durationMs + ~150 ms`（マシン→CF→EC2 の往復）なので、レグの大半は OpenAI chat call そのもの。
- ただし **OpenAI 側の tail latency** が断続的に ~3.5 s へ跳ねる（6回中1回）。固定のネットワークコストではないので、**warm client pool では消せない**（TLS は ~200-500 ms に過ぎない）。これが実機ベンチで translate leg が 2103 vs 3741 とばらついた正体。

### 2. ゲート #2 を 1500 ms → 2500 ms へ再ロック

Galaxy S10 の実バジェット: recognise ~900 ms（オンデバイス ML Kit の下限）+ translate median ~600 ms（tail ~3.5 s）+ BLE ~200 ms ≈ **median ~1700 ms**。p95 は OpenAI tail に引っ張られる。→ **1500 ms はどのコード lever でも到達不可**（だからこそ provisional / device-confirm だった）。

ユーザー判断で **`p95(ocr_system_latency_ms) <= 2500 ms`** に再ロック。会話 go/no-go 帯（1.5-2.5s）と一致し、OCR は看板/メニューを読む非リアルタイム用途なので妥当。アーキテクチャ自体は健全（median translate ~600 ms は良好）であり、ゲートが厳しすぎただけ。

修正箇所:
- `tools/latency_report.py`: `S3_TARGET_OCR_SYSTEM_MS = 2500.0`、ヘッダ docstring + 定数コメントに device-confirm の根拠を記載。
- `tools/test_latency_report.py`: pending テストの期待文字列を「vs 2500 ms」に、latency-FAIL テストを system=3000（> 2500）へ更新。
- `docs/codex/S3_TASKS.md`: 基準 #2 本文・Day 6 表（新規行 + post-redeploy bench 段落）・`--s3` ゲート記述・Open questions #2 を resolved に更新。
