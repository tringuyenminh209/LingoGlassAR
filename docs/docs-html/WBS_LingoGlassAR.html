■ §1　計画方針・前提
見積手法ボトムアップ（DD-LGA-001 で確定したクラス図・モジュールに基づき、各タスクを 0.5〜3 人日に分解）+ ファンクションポイント概算でクロスチェック
1 人日の定義1 人 × 8 時間。Solo founder の実働は 1 日 6〜7 時間想定のため、人日見積に 1.2 倍バッファ を内包
階層Lv1 = マイルストーン（S0〜S5 = M0〜M5）／ Lv2 = サブフェーズ／ Lv3 = 0.5〜3 人日の作業単位
タスク粒度Lv3 タスクは 1〜3 人日が原則。3 人日超は Lv4 に分割するか、リスクとして §6 に記載
依存関係S0 → S1 → S2 → S3 → S4 → S5（基本順序）。S2 と S3 の一部は並行可能、S4 と S5 の準備は重ねる
合否ゲート各マイルストーン末に Go/No-Go ゲート。No-Go なら scope を削る or 1 週延長。3 週連続超過なら全体見直し
AI agents の役割コードスケルトン生成（API handlers、Riverpod provider）／ テストケース生成／ ログ解析。1 人日 → 0.5〜0.7 人日に短縮できるタスクに反映済み

■ §5　Critical Path 分析
経路 A（Critical）：
1.2.2 S0 ゲート (1 pd)→ 2.2.2 BleClient (2 pd)→ 3.3.1 WsSessionHandler (2 pd)→ 3.3.2 MicCapture+WsClient (2 pd)
↓
3.4.3 S2 ゲート K-01 (1 pd)→ 4.3.3 S3 ゲート K-03 (1 pd)→ 5.1.2 ファーム移植 (3 pd)→ 5.3.2 屋外 readability K-06 (2 pd)
↓
5.4.2 S4 ゲート (1 pd)→ 6.2.2 本パイロット 5-10 名 (5 pd)→ 6.3.4 S5 ゲート Go/No-Go (1 pd)
Critical Path 累計 = 21 人日（直接 path 上）。残り 59 pd は path 上タスクの遅延を吸収可能。
運用ルール： Critical Path 上のタスクが 1 人日遅延した場合、その後のすべての Go/No-Go ゲート日付を 1 日後ろにスライド。並行可能タスク（6.1.1〜6.1.3 のパイロット準備）は W11〜W12 に前倒し実施することで吸収可能。
